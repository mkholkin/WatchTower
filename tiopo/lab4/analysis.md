# Выводы по ЛР №4

Итоговый запуск: `20261011t214228-cfa496`, 12 октября 2026 года по московскому времени. Стенд: выделенная Colima VM, Linux aarch64, Ubuntu 24.04.4, ядро 6.8.0-117, Docker 29.5.2, cgroup v2, четыре vCPU и около 5,77 GiB доступной RAM. Лимиты контейнеров приведены в [методике](README.md).

Первая серия исключена из итоговых измерений из-за коррекций часов Lima. Для повторной серии синхронизация временно отключена в выделенной VM; отчёт проверяет смещение wall/monotonic и допустимость длительностей. Исходные данные исключённой серии сохранены без исправлений.

## Рост нагрузки

В ступенчатом тесте получен 9 341 измеренный запрос. Ступени 1, 2, 4 и 8 VU выполняют выбранный SLO. При 8 VU p95 равен 104 мс, медиана пропускной способности — 71 RPS. Ступень 16 VU пограничная: p95 = 507 мс, чуть выше порога 500 мс; при 32 VU — уже 1144 мс. На этих двух ступенях неожиданных ответов ещё нет.

При 64 VU 15,46% запросов завершаются неожиданно, при 128 VU — 95,54%. Основной отказ — двухсекундный таймаут входа. Поэтому увеличение числа пользователей после насыщения не даёт устойчивого роста полезной пропускной способности.

API достигает примерно 100% одного ядра, тогда как генератор сохраняет большой запас CPU. Основная задержка проявляется при входе. Это согласуется с CPU-затратной проверкой bcrypt в `internal/service/auth/service.go`; точное распределение времени по функциям потребовало бы CPU-профиля.

Наблюдаемая граница между 8 и 16 VU относится к заданному сценарию с частой авторизацией, оборудованию и двадцатисекундным ступеням. Для определения точной ёмкости около порога нужны более длинные повторные ступени; это не универсальный предел WatchTower.

## Перегрузка и восстановление

После 30 с при 4 VU нагрузка повышалась до 128 VU на 45 с, затем возвращалась к 4 VU на 90 с. Baseline выполнял SLO; медиана успешного RPS — 36. Перегрузка вызвала таймауты, а после её снятия нормальные запросы ещё некоторое время завершались ошибками.

Первое здоровое пятисекундное окно началось через **70 с** после снятия перегрузки. Три последовательных окна подтвердили восстановление через **85 с**. Для подтверждения требовались p95 ≤ 500 мс, доля неожиданных ответов ≤ 1% и успешный RPS ≥ 28,8. Измерено восстановление пропускной способности и задержек, а не только доступность health endpoint.

Вся 90-секундная фаза восстановления не выполняет SLO, поскольку её сводная статистика включает первые 70 с с ошибками. Восстановление подтверждено по последовательным окнам в конце этой фазы.

Клиентский таймаут равен двум секундам. Задержки неуспешных запросов около 2000 мс отражают этот предел: они не измеряют, когда сервер фактически закончил обработку. Длительное восстановление согласуется с накопленной CPU-работой, которая не исчезает сразу после прекращения клиентских ожиданий.

## Стабильная нагрузка и ошибочные действия

Каждый из трёх профилей выполнялся 300 с при 4 VU после прогрева. Неожиданных ответов не было.

| Ошибочные действия | Запросов | p95, мс | p99, мс | Общий RPS, медиана | Успешный корректный RPS, медиана |
|---:|---:|---:|---:|---:|---:|
| 0% | 10650 | 69 | 97 | 36.0 | 36.0 |
| 10% | 10670 | 66 | 94 | 36.0 | 32.4 |
| 20% | 10660 | 69 | 101 | 36.0 | 28.8 |

Намеренные 401/400 не ухудшили наблюдаемые задержки или общий RPS. Снижение успешного корректного RPS до 32,4 и 28,8 связано с исключением заданных 10% и 20% ошибочных операций из этой метрики. Оно не означает возникновение неожиданных отказов. Небольшие различия задержек между одиночными прогонами не доказывают ускорение или замедление.

## Ресурсы

При стабильной нагрузке медиана CPU API составляет 24,5–24,9% одного ядра, PostgreSQL — 2,8–3,0%, Redis — около 1,1%. RAM API находится в пределах 11,0–17,4 MiB. Память PostgreSQL растёт по мере прогрева данных и находится в пределах 52–78 MiB; это само по себе не доказывает утечку. Пять минут наблюдения не исключают долговременные проблемы.

В этих тестах основную запись на диск выполняет PostgreSQL: медиана около 96 KiB/s в профилях 0/10% и около 64 KiB/s при 20%. В последнем случае некорректный PATCH отвергается до обновления записи. Нулевые или близкие к нулю физические чтения ожидаемы для небольшого набора данных в кеше и не означают отсутствие SQL-запросов.

Генератор и сборщик имеют запас CPU и памяти. Перегрузка API в ramp/stress не вызвана насыщением генератора. Подробные min/median/max для всех шести компонентов — в [таблицах измерений](results.md), распределения и настройки — в [measurements.json](measurements.json).

## Проверка выполнения

Пять профилей, 45 164 измеренных запроса. Все проверки полноты, изоляции, одинаковых лимитов и времени пройдены. Максимальный наблюдаемый скачок wall/monotonic-смещения — около 25 микросекунд, существенно ниже порога 20 мс. В Allure — пять завершённых экспериментов; статус означает корректность измерений, а не выполнение SLO под перегрузкой.

`make lab4-check`: 3 JS-теста и 10 Python-тестов. Отдельно проверены ожидаемые ошибки, нулевые окна RPS, перцентили, три последовательных окна восстановления, cgroup I/O, скачки часов, сохранение Allure при ошибке и очистка при SIGTERM. GitHub Actions настроен; приведённые здесь измерения получены локально в Docker.
