# ЛР №4 — нагрузочное тестирование

Испытывается реальный HTTP API WatchTower с PostgreSQL 18, Redis 7.4 и локальным HTTP-ресурсом. Миграции, авторизация, SQL-запросы и фоновые проверки работают как в приложении. Генератор — k6 1.3.0. Это HTTP-сценарий пользователя; браузерный UI и его отрисовка в измерение не входят.

## Запуск

Нужны Docker Engine с Compose, минимум 4 доступных ядра, 6 GiB RAM, Python 3.10+ и Node.js 24+ для проверки модели сценария. Нужен Linux с cgroup v2; Docker Desktop/Colima предоставляют его через VM. При меньшем числе ядер запуск явно завершается ошибкой.

```sh
make lab4-check
make lab4-smoke
make lab4
```

Полный прогон занимает около 25 минут плюс сборка образов. На macOS можно создать отдельную VM без переключения глобального контекста:

```sh
colima start watchtower-lab4 --vm-type vz --cpu 4 --memory 6 --disk 20 --activate=false --ssh-config=false --mount "$PWD:w"
# Только в выделенной тестовой VM: исключить коррекции часов во время замеров.
colima ssh --profile watchtower-lab4 -- sudo systemctl stop lima-guestagent.service systemd-timesyncd.service
DOCKER_CONTEXT=colima-watchtower-lab4 make lab4
colima ssh --profile watchtower-lab4 -- sudo systemctl start systemd-timesyncd.service lima-guestagent.service
colima stop watchtower-lab4
```

Артефакты: `build/lab4/runs/<run-id>/`, путь последнего запуска — `build/lab4/latest.txt`. Открыть Allure:

```sh
python3 -m http.server 8088 --directory "$(cat build/lab4/latest.txt)/allure-report"
```

Адрес: <http://localhost:8088>. В каждом тесте Allure есть статистика и три изображения: задержки, пропускная способность, ресурсы. Статус `passed` означает корректное завершение и полноту эксперимента; выполнение SLO описано отдельно в данных. Smoke помечается `skipped` и не заменяет полные измерения.

На macOS runner удерживает систему от автоматического сна через `caffeinate` на время работы. Закрытие крышки или ручной сон всё равно может прервать измерения: разрывы мониторинга и скачки времени приводят к отклонению результатов. Сборщик сравнивает wall clock с монотонными часами: изменение смещения более чем на 20 мс за интервал делает профиль недостоверным, даже если все запросы успешны. Отрицательные длительности также отклоняются. Это важно для Lima, которая может корректировать часы скачками; службы восстанавливаются после измерений. Скорости I/O рассчитываются по монотонному интервалу.

Для отладки одного профиля: `python3 tools/lab4/run.py --smoke --profile soak-20`. Полная работа требует всех пяти профилей. В CI `.github/workflows/tiopo-lab4.yml` выполняет весь набор и сохраняет отчёты даже при ошибке. Прогресс k6 виден в логах во время выполнения.

## Нагрузка

Один сеанс состоит из десяти запросов: вход; создание монитора; список; детали; история проверок; SLA; изменение названия; повторное чтение; удаление; список после удаления. Затем пользователь ждёт 0,8–1,2 с. Следующий сеанс снова выполняет вход. Для каждого VU используется отдельный пользователь. Подготовка регистрирует пользователей и создаёт один постоянный монитор общего ресурса, чтобы проверять нагрузку на рабочую систему без гонки первоначального создания одной цели.

| Профиль | Нагрузка после прогрева |
|---|---|
| `ramp` | 1, 2, 4, 8, 16, 32, 64, 128 VU, по 20 с на ступень |
| `stress` | 4 VU × 30 с → 128 VU × 45 с → 4 VU × 90 с |
| `soak-0` | 4 VU × 300 с, корректные операции |
| `soak-10` | 4 VU × 300 с, один ошибочный запрос на 10 |
| `soak-20` | 4 VU × 300 с, два ошибочных запроса на 10 |

Каждый профиль начинается с прогрева 15 с при 2 VU. Первая секунда каждой ступени — переход к заданному числу VU. На завершение уже начатого сеанса при снижении нагрузки даётся 5 с, в конце сценария — 10 с. Поэтому фактическое число активных пользователей сразу после спада может временно превышать заданное.

В `soak-10` чтение деталей без токена должно вернуть 401. В `soak-20` дополнительно передаётся число вместо строкового названия, ожидается 400. Эти ответы учитываются отдельно. Иной код, таймаут или некорректный результат входа/создания считается неожиданной ошибкой. При неудачном входе или создании сеанс прекращается; наблюдаемая доля ошибочных операций сохраняется, а не подменяется заданными 10/20%.

## Изоляция и наблюдение

| Компонент | CPU | Квота CPU | RAM |
|---|---:|---:|---:|
| API, `GOMAXPROCS=1` | 0 | 1 | 768 MiB |
| PostgreSQL | 1 | 1 | 1 GiB |
| Redis | 1 | 0,25 | 128 MiB |
| Локальный HTTP-ресурс | 1 | 0,1 | 128 MiB |
| k6 | 2 | 1 | 512 MiB |
| Сборщик метрик | 3 | 0,25 | 256 MiB |

Для каждого профиля создаётся отдельный образ API с уникальной меткой, контейнеры, сеть и дисковый том PostgreSQL. Код и лимиты одинаковы; меняются только идентификатор запуска, временный JWT-секрет и профиль генератора. Данные предыдущего профиля не переносятся. Порты приложения на хост не публикуются. Настройки и идентификаторы образов сохраняются в `manifest.json` и `profiles/*/inspect.json`. Контейнеры, сети и тома удаляются в `finally`; журнал очистки остаётся в артефактах. Образы сохраняются для воспроизводимости.

Сборщик раз в секунду читает Docker Engine API и cgroup v2 `io.stat`. Сокет Docker и cgroup смонтированы только для чтения; код сборщика выполняет только GET-запросы. Доступ к Docker socket предполагает доверенный локальный стенд. CPU рассчитывается по приращению счётчиков и выражается в процентах одного ядра. RAM — working set без inactive file cache. Диск — физически учтённые cgroup байты чтения/записи в секунду: попадания в кеш не увеличивают счётчик. Пустой читаемый `io.stat` означает нулевой I/O; недоступный счётчик остаётся отсутствующим и приводит к ошибке проверки полноты. GPU не используется.

На одной машине генератор, мониторинг и система не делят ядра. ОС и Docker daemon остаются общей инфраструктурой; это ограничение локального стенда. Графики ресурсов генератора и сборщика позволяют проверить, не стали ли они узким местом.

## Статистика и критерии

Из статистики исключены подготовка, прогрев и завершение. Полное время каждого запроса измеряется на клиенте, включая ожидание соединения и передачу ответа. Разрешение `Date.now()` — 1 мс: значение 0 означает запрос короче разрешения таймера. `p50/p75/p90/p95/p99` — nearest-rank по отдельным запросам, без усреднения перцентилей разных сеансов. Сохраняются временной ряд, эмпирическая функция распределения и гистограмма. Дополнительно есть задержки успешных корректных операций и разрез по endpoint.

RPS рассчитывается в фиксированных окнах по 5 с, включая пустые окна; сохраняются min/max/mean/median и те же перцентили. Общий RPS и RPS успешных корректных операций различаются. Результат относится к закрытой модели пользователей с паузами и не является максимальной пропускной способностью произвольного endpoint.

Для анализа принят SLO: p95 ≤ 500 мс, неожиданные ответы ≤ 1%. Ступени `ramp` классифицируются по этому критерию. После `stress` восстановление подтверждается тремя последовательными пятисекундными окнами, выполняющими SLO и достигающими ≥ 80% медианы успешного RPS baseline. Отчёт содержит начало первого подходящего окна и момент подтверждения после 15 с наблюдения. Отсутствие перегруза или неподтверждённое восстановление указывается явно.

Полный профиль должен содержать минимум 1000 измеренных запросов; каждый soak длится не менее 300 с. Ресурсы представлены иерархически по профилю/компоненту/метрике, с min/median/max и графиками. Пять минут позволяют увидеть краткосрочную динамику, но не доказывают отсутствие долговременной утечки. Профили выполняются по одному разу: межпрогонная вариативность не оценена.

Фактические измерения и выводы — в `results.md` и `analysis.md` рядом с этим файлом. Полные исходные метрики и логи — в локальных артефактах и GitHub Actions artifact.

Методика опирается на [сценарии k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/), [завершение итераций](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/graceful-stop/) и [Docker Engine stats](https://docs.docker.com/reference/api/engine/version/v1.51/).
