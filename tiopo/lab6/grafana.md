# Grafana, Prometheus и Tempo для ЛР №6

Стенд открывает сохранённые измерения ЛР №6 в Grafana и трассы в Tempo. Импорт сохраняет исходные временные метки. В новой серии OpenTelemetry Collector передаёт трассы в Tempo во время нагрузки; отдельный стенд просмотра показывает уже сохранённые артефакты. Серия `20261124t091051-515010` остановлена по запросу пользователя после 11 завершённых опытов; результаты приведены в [results.md](results.md).

## Запуск

Нужны локальный Docker Engine с Unix socket, Docker с Compose, Python 3 и сохранённый каталог полного запуска, указанный в `build/lab6/latest.txt`.

```sh
make lab6-grafana
make lab6-grafana-check
```

Для выбора другого каталога:

```sh
make lab6-grafana RUN_DIR="/путь/к/распакованному/runs/<run-id>"
```

Параметр `RUN_DIR` также поддерживается командами `lab6-grafana-check` и `lab6-grafana-down`. По умолчанию проверка ресурсов занимает 5 секунд; для другого окна задайте `LAB6_VIEW_SECONDS=60`.

Открыть [дашборд ЛР №6](http://localhost:3036/d/lab6-observability). Grafana доступна локально без входа с правами Viewer. Сервисы слушают только loopback: Grafana — порт 3036, Prometheus — 9096, Tempo — 3206, OTLP — 4316. Не публикуйте эти порты наружу.

Остановка:

```sh
make lab6-grafana-down
```

## Импорт измерений

Импортёр читает сырые `resources.jsonl` и сводку `summary.json` выбранного запуска. Из них формируется OpenMetrics, затем `promtool tsdb create-blocks-from openmetrics` создаёт блоки для Prometheus. Исходные временные метки сохраняются; часы опытов не сдвигаются к моменту просмотра. Рабочие файлы стенда находятся в `build/lab6/grafana/<run-id>/`.

Provisioning подключает Prometheus с UID `lab6-prometheus` и Tempo с UID `lab6-tempo`. JSON дашборда хранится в `tools/lab6/grafana/dashboards/lab6.json`; при подготовке рабочей копии импортёр выставляет абсолютный диапазон времени по выбранным артефактам. Если выбрать «последний час» вместо этого диапазона, исторические данные могут исчезнуть с графика.

`lab6_cpu_seconds_total` — накопленный CPU-счётчик контейнера в секундах. График показывает `rate(...[10s]) * 100`: 100% соответствует одному полностью занятому ядру. `lab6_memory_bytes` — working set Docker без inactive file cache; на дашборде байты переведены в MiB. На графике RAM скрываются отсчёты старше пяти секунд, чтобы стандартный lookback Prometheus не продлевал завершённый опыт.

Сводные метрики `lab6_summary_cpu_seconds`, `lab6_summary_memory_bytes`, `lab6_summary_rps`, `lab6_summary_unexpected_ratio` сохраняют значения отчёта за измерительное окно. CPU — приращение счётчика между границами окна, RAM — min/median/max, RPS — медиана, ошибки — доля неожиданных ответов. Ожидаемые ответы 401/400 не приравниваются к неожиданным ошибкам. Сводные панели используют `last_over_time` с фиксированным окном загруженного запуска и привязкой `@` к его окончанию. Поэтому итоговые CPU/RAM и показатели нагрузки доступны и при instant-запросах с нулевым диапазоном времени. Приближение графика меняет временной ряд, а итоговая статистика остаётся рассчитанной за весь опыт.

## Чтение дашборда

В фильтрах выбрать запуск, профиль, варианты, повторение и компонент. Обзор показывает один профиль, одно повторение и выбранный компонент. В каждом сравнении четыре столбца: без диагностики, трассировка, расширенные логи, оба режима. Цвет каждого режима одинаков на всех панелях. Основные показатели — CPU за опыт, медиана памяти, медиана RPS и неожиданные ошибки. Для ресурсов выберите в фильтре «Компонент» приложение (`api`), Docker-сборщик (`collector`), OpenTelemetry Collector (`otel-collector`) или Tempo (`tempo`).

Нажатие на столбец открывает дашборд «ЛР №6 — один опыт подробно». Ссылка передаёт режим, компонент и точные границы измерительного окна. Наверху показаны CPU за опыт и минимум / медиана / максимум памяти; ниже — два графика с одной кривой каждый. Ссылка «К сравнению режимов» возвращает в обзор. Для другого опыта выбирайте его столбец в обзоре: так временной диапазон соответствует выбранному режиму.

Опыты выполнялись последовательно. Обзор сравнивает итоговые показатели одинакового сценария; графики деталей сохраняют фактическое время, без искусственного совмещения осей. Поля `window_start_ms` и `window_end_ms` в сводных метриках используются только для перехода к нужному временному окну.

## Просмотр трасс

Нажмите «Трасса HTTP → SQL» в обзоре или деталях опыта. Страница `/d/lab6-traces` открывает пример текущего запуска автоматически и доступна гостевому Viewer. Таблица показывает HTTP- и SQL-операции с длительностью; ниже расположено дерево spans. Для другой трассы введите её ID в поле «ID трассы».

Ссылки на примеры содержат ID загруженного артефакта. При смене артефакта используйте «Пример текущего запуска», чтобы открыть его трассу.

Если в адресе остались фильтры или время предыдущего запуска, нажмите «Показать данные текущего запуска». Кнопка задаёт правильный диапазон Unix milliseconds и доступные значения фильтров. Список профилей и повторений формируется из загруженных результатов; отсутствующие опыты в нём не показываются.

## Стоимость просмотра

API, Docker-сборщик, OpenTelemetry Collector и Tempo измеряются во время нагрузки в новой матрице OpenTelemetry. Grafana, Prometheus и Tempo измеряются отдельно после импорта: `viewer-resources.jsonl` хранит сырые Docker-счётчики; `viewer-resources.json` в рабочем каталоге содержит сводку CPU в секундах и RAM min/median/max трёх контейнеров за выбранное окно работы стенда. Сохранённая сводка этого измерения — `tiopo/lab6/grafana-resources.json`.

Это стоимость последующего просмотра сохранённых данных. Она не измеряет накладные расходы live-экспорта трасс в Tempo под исходной нагрузкой. Сравнивать её напрямую с CPU API в опытах или прибавлять к нему без общего измерительного окна нельзя. Общие ресурсы Docker daemon, ОС и VM полностью по контейнерам не распределяются.

## OpenTelemetry

В новой матрице трассы поступают в Tempo во время нагрузки через OpenTelemetry Collector. `tempo-live-check.json` и `tempo-live-trace.json` подтверждают доставку и связь HTTP → SQL до остановки стенда. Collector сохраняет исходный OTLP JSONL в `traces-otlp.jsonl`. Повторный импорт в стенд просмотра сохраняет исходные trace ID, 64-битные span ID и временные метки.

Счётчики SDK и Collector сверяются с файловым экспортом в отчёте. Производный `traces.jsonl` используется для Chrome Trace и совместимого просмотра исторических запусков.
