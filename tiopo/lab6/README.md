# ЛР №6 — стоимость трассировки и расширенных логов

Повторяем пять HTTP-профилей ЛР №4 в четырёх вариантах: `baseline` — обе функции выключены, `trace` — трассировка, `debug` — расширенные HTTP-логи, `trace-debug` — обе функции. Генератор k6, данные, прогрев и ограничения ресурсов одинаковы. Код сценариев, сборщик Docker-метрик и расчёт статистики запросов переиспользованы из ЛР №4 без изменений.

## Запуск

Нужны Docker Engine с Compose, минимум 4 ядра и 6 GiB RAM, Python 3.10+ и Node.js для проверки сценария. Изолированный стенд и ограничения Docker Desktop/Colima описаны в [ЛР №4](../lab4/README.md).

```sh
make lab6-check
make lab6-smoke
make lab6
```

Smoke проверяет запуск и сбор артефактов; в Allure он имеет статус `skipped`. Полный запуск повторяет `ramp`, `stress`, `soak-0`, `soak-10`, `soak-20` для каждого варианта и занимает около 100 минут плюс сборка образов. Каждый soak содержит 300 секунд после прогрева. Ошибочные операции 401/400 и неожиданные ошибки различаются по правилам ЛР №4.

Артефакты находятся в `build/lab6/runs/<run-id>/`; путь последнего запуска — `build/lab6/latest.txt`. Allure открывается локально:

```sh
python3 -m http.server 8088 --directory "$(cat build/lab6/latest.txt)/allure-report"
```

В браузере открыть <http://localhost:8088>. Исходные данные каждого опыта лежат в `variants/<variant>/repetitions/<repetition>/profiles/<profile>/`: `requests.jsonl`, `k6-summary.json`, `resources.jsonl`, логи, сведения о контейнерах и, при трассировке, `traces.jsonl`. JSON-сводка — `summary.json`, таблица — `results.md`, графики — `plots/`. Отчёт можно пересчитать через `python3 -m tools.lab6.report <run-directory>` в окружении с matplotlib.

## Что измеряется

Измерительное окно совпадает с ЛР №4: от конца прогрева до планового конца нагрузки. Для API и сборщика метрик отдельно берётся приращение `raw.cpu_stats.cpu_usage.total_usage`, делённое на 10⁹: единица — CPU-секунда. Значения на границах окна линейно интерполируются между соседними сырыми отсчётами; это приближение равномерного расхода CPU внутри интервала около секунды. Отсчёты должны покрывать обе границы; сброс счётчика, отсутствие значения или разрыв более пяти секунд отклоняют опыт. Проценты CPU не суммируются.

RAM — working set Docker без inactive file cache; отчёт показывает минимум, медиану и максимум отсчётов внутри окна. Для каждого компонента рассчитываются абсолютные разницы CPU и RAM с `baseline` того же профиля и повторения. Для CPU дополнительно приводится относительная разница; при нулевом baseline она отсутствует. Потребление самого сборщика не прибавляется к API.

Рядом с ресурсами указаны медиана RPS, доля неожиданных ошибок и фактическая доля ожидаемых ошибочных операций. Подробная статистика запросов, задержки, этапы нагрузки и проверка восстановления после stress сохраняются в JSON из расчёта ЛР №4. Закрытая модель пользователей может дать меньше запросов при замедлении, поэтому снижение CPU само по себе не означает ускорения. Проверяются одинаковые профили и лимиты контейнеров, полнота мониторинга, скачки часов, OOM и рестарты.

## Трассы и логи

Трассировка включается через `WT_TRACE_FILE`, расширенные HTTP-логи — через `WT_HTTP_DEBUG`. Используется собственный внутрипроцессный экспортёр JSONL. Каждая завершённая операция содержит идентификаторы трассы и span, родителя, имя операции, начало в Unix-наносекундах, длительность и статус. HTTP-операция хранит метод и шаблон маршрута; SQL-операция — только тип команды. Тела, query string, заголовки, токены и аргументы SQL в экспорт не входят. HTTP-обработчик создаётся через `gin.New` без стандартного логгера URL, чтобы query string не попадала в журнал; переключение обычных и расширенных сообщений использует уровни info/debug проектного логгера.

Отчёт проверяет схему и имена операций, требует непустую трассу при включённом режиме и события внутри измерительного окна. Он создаёт рядом `trace.json` с `traceEvents` формата Chrome Trace Event; файл можно открыть в совместимом просмотрщике трасс. Исходный JSONL сохраняется для аудита. Настройка выключенной трассировки не должна создавать события. Тесты проверяют отсутствие секретов и сырых идентификаторов маршрута.

Запись трасс и расширенных логов входит в измеряемую стоимость. ОС и Docker daemon остаются общими ресурсами стенда. Один опыт на комбинацию не оценивает вариативность между запусками; выводы должны учитывать RPS и ошибки и не доказывают долговременную устойчивость. Статус `passed` в Allure подтверждает целостность опыта, а не выполнение SLO или отсутствие накладных расходов.

Фактические [результаты](results.md), [выводы](analysis.md), [JSON-сводка](measurements.json) и [таблица требований](requirements.md) сохранены после полного прогона. Smoke и синтетические тестовые данные не заменяют измерения. CI сохраняет сырые данные, трассы и отчёты, в том числе при ошибке опыта.

## Интеграция в API

Для обычного запуска трассировка включается переменной `WT_TRACE_FILE` с путём к новому файлу JSONL. Каталог должен существовать и быть доступен пользователю API. Уже существующий файл не перезаписывается. Без переменной recorder отсутствует, SQL hooks не устанавливаются и события не создаются. `X-Trace-ID` позволяет сопоставить ответ с HTTP span и дочерними PostgreSQL spans.

Расширенные HTTP-логи включаются `WT_HTTP_DEBUG=true` вместе с `logging.level: debug`. Уровень по умолчанию — `info`; в сравнении используется стандартный slog JSON writer в stdout и Docker json-file sink. В HTTP-диагностику входят только метод, шаблон маршрута, статус, длительность и размер ответа, при трассировке также trace ID. Динамические ID, query string, тела, заголовки, SQL-текст и аргументы не экспортируются. Вместо Gin URL-логгера используется этот обработчик, чтобы токены в query string не попадали в логи.

Recorder — встроенный синхронный JSONL exporter. Сбор и запись событий происходят в процессе API: их CPU, RAM и файловые операции входят в стоимость API, отдельного процесса трассировки нет. PostgreSQL hooks используют контекст текущего запроса; `ContextWithFallback` обеспечивает передачу span через сгенерированные Gin-обработчики. Обрабатываются запросы, выполняемые через pgx Query/QueryRow/Exec; отдельная трассировка каждой операции Redis и фоновых служб не заявляется.

Для публичного репозитория workflow использует `ubuntu-24.04`: стандартный Linux runner предоставляет четыре CPU, что соответствует схеме изоляции. Характеристики runner описаны в [GitHub Docs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Runner дополнительно проверяет фактическое число CPU Docker перед началом опытов.

Матрица повторяет исходный HTTP-сценарий ЛР №4 с парольным входом; в её одноразовом API MFA выключена. Это сохраняет тот же состав запросов и позволяет сравнивать именно стоимость наблюдаемости. Проверка UI и стоимость двухфакторного входа относятся к другому сценарию.

Семплирование не используется: записываются все инструментированные операции. В Chrome Trace Event JSON поле tid обозначает логическую трассу запроса, а не поток ОС; полный trace_id сохранён в args. Для опытов с трассировкой Chrome JSON приложен непосредственно к результату Allure.

## Повтор локального запуска с кэшированными образами

Если в выделенной VM сохранены указанные образы ЛР №4, текущий API можно пересобрать без сети:

```sh
DOCKER_CONTEXT=colima-watchtower-lab4 python3 tools/lab6/run.py \
  --runtime-base watchtower-lab4-app:20261011t214228-cfa496 \
  --postgres-image watchtower-lab4-postgres:20261011t214228-cfa496
```

VM предварительно запускается по инструкции ЛР №4. Для smoke добавляется `--smoke`, для повторов — `--repetitions N`. Обычный `make lab6` собирает runtime и PostgreSQL с нуля. Каждый опыт получает отдельный образ с меткой запуска; идентификаторы базовых и экспериментальных образов сохраняются в manifest.json.
