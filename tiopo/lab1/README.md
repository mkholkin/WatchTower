# ТИОПО. Лабораторная работа № 1

## Цель и объект тестирования

Модульное тестирование бизнес-логики и доступа к данным WatchTower по [заданию](../ТИОПО,%20ЛР%20№1.pdf). WatchTower проверяет доступность сетевых ресурсов, агрегирует результаты проверок, рассчитывает SLA и отправляет уведомления при смене статуса.

Основной поток приложения: планировщик → HTTP-проверка → сохранение результата → анализ состояния монитора → сводка и уведомление. Сервисы управления мониторами, контактами и окнами обслуживания используют репозитории PostgreSQL; Redis кэширует последние сводки. Авторизация основана на JWT. HTTP API и CLI вызывают те же сервисы.

В согласованный объём входят 22 пакета, перечисленные в [packages.txt](../../tools/lab1/packages.txt): доменные объекты с поведением, бизнес-сервисы, DTO и преобразования, HTTP evaluator, все основные PostgreSQL-репозитории и Redis-декоратор. MongoDB, UI, HTTP/gRPC-транспорт, реальные сетевые пробы и провайдеры доставки, benchmark-программы и незавершённые TCP/ICMP-проверки не входят в лабораторную. Проверки констант протокола и преобразования TCP/ICMP DTO включены, поскольку это уже реализованное поведение основных компонентов.

## Запуск

Нужны Go 1.26.3, Node.js 24 или новее с npm, Python 3 и Make. Для изолированного запуска нужен Docker. Команды выполняются из корня проекта.

```sh
# Однократная подготовка с доступом к сети.
make lab1-prepare

# Модульные тесты, покрытие строк и ветвей, HTML-отчёт Allure.
make lab1
make allure-open

# Отдельные проверки.
make test-unit
make test-unit-shuffle SEED=42
make test-unit-shuffle SEED=2026
make test-unit-race
make test-processes
go test ./...
```

`make test` — алиас `make test-unit`. Каждый запуск использует `-count=1`, поэтому результат не берётся из кэша тестов. Тесты не запускают PostgreSQL, Redis или Testcontainers. Готовые GoMock-моки хранятся в репозитории; их перегенерация вынесена в отдельную команду `make mocks`.

В командах проверки отключена загрузка Go-модулей (`GOPROXY=off`, `GOSUMDB=off`); при отсутствии зависимости нужно выполнить `make lab1-prepare`. Обычный локальный запуск не изолирует сетевой стек ОС — такую изоляцию обеспечивает отдельный Docker-запуск ниже.

`make allure-report` генерирует отчёт для последнего обычного прогона. Для другого прогона, например случайного порядка, выполните `LAB1_RUN=shuffle-42 make allure-report`. Ошибки тестов сохраняют ненулевой код завершения, при этом отчёт всё равно формируется.

Артефакты находятся в `build/lab1/`:

- `allure-report/index.html` — самостоятельный HTML-файл Allure с результатами, шагами, suite/method, техниками, стилем, PID и seed;
- `runs/latest/tests.jsonl`, `summary.json`, `cases.json`, `cases.md`, `allure-results/` — стандартный Go JSON и результаты текущего прогона;
- `runs/shuffle-42/`, `runs/shuffle-2026/`, `runs/race/`, `runs/processes-serial/` — независимые дополнительные прогоны;
- `coverage.html`, `coverage.xml`, `coverage.out`, `statements.txt` — исходники с покрытием, Cobertura, Go coverprofile и statement coverage;
- `branches/*.log`, `branches/*.json` — отчёты gobco по каждому пакету с непокрытыми ветвями.

Каталог `build/` и установленные инструменты исключены из Git; они воспроизводятся командами выше. Снимок матрицы сценариев для сдачи находится в [test-cases.md](test-cases.md). Актуальная матрица автоматически строится из Allure при каждом прогоне.

## Организация тестов

Используются стандартные `testing`, `testify`, GoMock, `pgxmock/v4` и `redismock/v9`. Для отчётности подключён официальный `allure-go/commons/gotest` 1.3.1 и CLI Allure 3.17.0 с npm lock-файлом. Вспомогательный `testutil.Case` только добавляет метаданные к обычному Go-тесту. Вложенный стандартный `t.Run` позволяет дождаться `t.Cleanup`, включая проверку ожиданий моков, до завершения результата Allure. Отдельный тест в `tools/lab1/reporting_test.go` проверяет, что ошибка очистки fixture отражается в Allure как падение.

**Классический стиль** используется для доменных объектов, валидации, преобразований, JWT и HTTP evaluator: проверяются настоящие объекты и возвращаемые значения. **Лондонский стиль** применяется к сервисам и репозиториям: зависимости заменены моками или небольшими записывающими stub-объектами, проверяются аргументы, ошибки и взаимодействия на границах компонентов.

PostgreSQL-тесты подключают `sqlcgen.New(pgxmock.DB)` к настоящим реализациям репозиториев. Исполняются сгенерированные запросы, связывание аргументов, сканирование строк и преобразование в доменные объекты. SQL сопоставляется по имени сгенерированного запроса, аргументы — по значениям: изменение форматирования SQL не ломает тест. Исполнение SQL сервером и ограничения схемы относятся к интеграционным тестам.

Каждая fixture создаётся заново. [ObjectMother](../../internal/testutil/fixtures.go) возвращает готовые валидные User, Target, Contact, MaintenanceWindow и Result. Data Builder `NewMonitorBuilder` позволяет менять отдельные свойства монитора, сохраняя понятный базовый сценарий. Общих изменяемых сущностей между тестами нет; ресурсы и моки очищаются через `t.Cleanup`.

Тесты соблюдают **Arrange → Act → Assert**. Arrange готовит входные данные и зависимости, Act вызывает одну проверяемую публичную операцию, Assert проверяет результат, состояние и взаимодействия. В подробных сценариях этапы видны как Allure steps; в компактных сервисных таблицах они обозначены в коде. Конструкторы используются для подготовки fixture, чтение состояния — для утверждений. Приватные методы напрямую не вызываются.

Фоновые `Run`/`StartLoop` тестируются управляемым циклом с каналами, отменой контекста и поддельными часами. Границы времени доменных окон проверяются через `testing/synctest`. Нет проверок вида «подождать фиксированное время и надеяться на завершение».

## Техники проектирования

Для каждого сценария техника и стиль записаны в метаданных Allure и в матрице тестов.

- **Классы эквивалентности (`equivalence`)**: валидные/невалидные данные, найденный/отсутствующий объект, успех/ошибка репозитория, корректный/неверный JWT.
- **Граничные значения (`boundary`)**: пустые строки и коллекции, HTTP-коды 99/100/599/600, отрицательная/нулевая задержка, длительность и границы окна обслуживания, предел задержки 999/1000/1001, нулевой лимит сводок, обрезка интервалов SLA.
- **Таблицы решений (`decision-table`)**: право владения и ошибка зависимости; совпадение протоколов; наличие и исправность кэша; сочетание кода ответа, задержки и сетевой ошибки.
- **Переходы состояний (`state-transition`)**: включение/отключение, повторное действие, привязка/отвязка, создание/обновление/удаление задания планировщика, смена статуса и уведомление.

Публичные операции основных компонентов имеют успешные и ошибочные сценарии; операции без ошибочного результата проверяются на альтернативных состояниях и идемпотентности. Конструкторы также проверяются через их наблюдаемое поведение. Два метода PostgreSQL ProbeSummary (`Create`, `BulkCreate`) намеренно ничего не сохраняют: сводки читаются из агрегированного представления. Для них проверяется существующий контракт с пустыми и заполненными входами, без фиктивных ожиданий SQL-записи.

В Go ожидаемые исключительные ситуации представлены `error`: тесты используют `ErrorIs`, `ErrorAs` и проверки доменных sentinel-ошибок. Panic не считается нормальным результатом бизнес-операции. Неизвестные PostgreSQL enum-значения проверяются как защита от рассогласования версий схемы; такие строки нельзя создать при текущих enum-ограничениях.

## Случайный порядок и процессы

`make test-unit-shuffle SEED=42` задаёт `go test -shuffle=42` и `LAB1_SEED=42`. Стандартный Go перемешивает верхнеуровневые тесты, `testutil.Shuffle` — табличные сценарии с локальным генератором на основе seed и имени теста. Повторение seed воспроизводит порядок внутри пакета; порядок вывода разных процессов может отличаться. Seed сохраняется в Allure, но вместе с PID исключён из идентификатора истории теста.

PID записывается непосредственно внутри тестового процесса через `os.Getpid()`. `summary.json` группирует выполненные сценарии по уникальным PID. Для выбранных 22 пакетов обычный запуск создаёт **22 тестовых процесса**, по одному тестовому бинарнику на пакет. `make test-processes` использует `-p=1`: всего процессов также 22, но одновременно выполняется только один пакет. `-p` ограничивает параллелизм пакетов и команд сборки, `-parallel` — тесты с `t.Parallel` внутри бинарника. Горутины фоновых сервисов не являются процессами ОС. Процесс `go`, компиляторы, Python и Allure в этот счётчик **тестовых** процессов не включены.

## Покрытие

```sh
make coverage
make coverage-branch
```

Покрытие измеряется готовыми инструментами, собственный вычислитель покрытия не реализован.

`go test -covermode=atomic -coverpkg=...` формирует профиль явно выбранных пакетов, включая вызовы из тестов соседних компонентов. `go tool cover` показывает **statement coverage**, поэтому его процент не называется покрытием строк или ветвей. `gocover-cobertura` 1.5.0 преобразует профиль в Cobertura XML и вычисляет **line coverage**; `summarize.py` только читает готовые атрибуты `lines-covered`, `lines-valid`, `line-rate`.

`gobco` 1.3.4 в режиме **`-branch`** отдельно инструментирует каждый пакет в временной копии, запускает тесты и выводит достигнутые true/false исходы условий и непокрытые ветви. Используется именно branch mode, без подмены метрики стандартным Go coverage или условным процентом по строкам. Суммарный результат — сумма числителей и знаменателей `Branch coverage` из отчётов пакетов. Gobco не измеряет все виды ветвления управляющего графа (например, `select`) и не учитывает полностью неиспользуемые функции без условий; это ограничения инструмента.

Сгенерированный SQLC, моки, тестовые helpers и заглушки файлов TCP/ICMP исключены из line coverage. Некоторые незавершённые TCP/ICMP-методы находятся в общих доменных файлах и остаются в знаменателе. Branch coverage собирается отдельно по коду каждого пакета и не объединяет межпакетные вызовы так же, как `-coverpkg`; поэтому эти проценты напрямую несопоставимы. Непокрытые пути видны в HTML и логах, порог 100% заданием не установлен.

## Исправления, обнаруженные тестами

- `service.Error` безопасен даже без причин; `Unwrap() []error` сохраняет причины для `errors.Is` и не содержит недопустимых nil-элементов.
- `Register` возвращает ошибку поиска пользователя в БД, не переходя к созданию учётной записи.
- Привязка и отвязка объектов проверяет владельца обеих сторон; создание монитора отвергает чужие контакты и окна обслуживания.
- `EnableMonitor` возвращает ошибку синхронизации target, а `CreateMonitor` сохраняет ошибку поиска target вместо продолжения создания.
- `UpdateMonitor` проверяет эффективную конфигурацию и ожидания до изменения объекта, записи в репозитории или публикации событий.
- `HTTPExpectations.Validate` реализован; `NewMonitor` проверяет HTTP-ожидания, включая nil и типизированный nil.
- Неуспешный `ApplyUpdate` контакта или окна обслуживания сохраняет исходное состояние объекта: изменения применяются после валидации копии.
- Redis-декоратор сохраняет запись в основной репозиторий при ошибке кэша, а повреждённый кэш инвалидирует и восстанавливает из БД.
- PostgreSQL `FetchUnprocessed` сохраняет текст ошибки сетевой проверки при преобразовании строки в доменный результат.
- Устаревшие вызовы методов в CLI приведены к текущим интерфейсам, чтобы `go test ./...` компилировал проект; обновлены устаревшие моки Prober и удалён недостижимый `return`.

Для изменений поведения сначала воспроизводились ошибки тестами, затем проверялся успешный прогон. Тесты проверяют возвращаемые значения, ошибки, значимые поля сохранённых объектов и события. Они не зависят от лог-сообщений, имён приватных функций или случайных UUID. Ожидаемый хеш Target задан независимо вычисленным литералом. Это позволяет менять внутреннюю реализацию при сохранении публичного контракта.

## Соответствие заданию и ограничения

Подробная [карта выполнения всех 15 требований](requirements.md) содержит ссылки на конкретные тесты, реализацию команд и результаты каждого пункта.

Пункты 1–2: сценарии публичных операций и ожидаемых ошибок перечислены в матрице. Пункт 3: присутствуют классический и лондонский стили. Пункты 4–6: AAA, fixtures, один Act, наблюдение через публичный контракт; исправления повышают тестируемость и корректность без выделения тестовых API. Пункт 7: Data Builder и Object Mother. Пункты 8–9: команды Make и автоматически генерируемый Allure. Пункт 10: воспроизводимое перемешивание. Пункт 11: контейнер без сети. Пункт 12: фактические PID и объяснение параллелизма. Пункты 13–14: результаты выполнения и обе метрики покрытия. Пункт 15: регрессии, независимые fixtures, контролируемое время и проверки контрактов.

Прежние PostgreSQL Testcontainers-тесты помечены `//go:build integration` и доступны отдельно через `make test-integration`. Их реальная инфраструктура и SQL-миграции не проверяются модульными тестами: исходный образ PostgreSQL 15 требует согласования с расширениями миграций. Это отдельный интеграционный контур, а не зависимость лабораторной.
