# ТИОПО. Лабораторная работа №2

Работа выполнена для WatchTower в ветке `TIOPO-2`. Интеграционные тесты проверяют сервисы вместе с PostgreSQL и Redis, E2E — HTTP API и фоновые проверки доступности. Результаты модульных тестов ЛР №1 и новых сценариев собираются в Allure.

## Запуск

Нужны Docker с Compose и Make. Из корня проекта:

```sh
make lab2
```

Команда собирает образ из текущего checkout, поднимает отдельный стенд, последовательно запускает `unit → integration → e2e`, сохраняет отчёт и удаляет контейнеры стенда. Первый запуск скачивает образы и зависимости. Go, Node, Allure, Python, curl, tcpdump и клиенты хранилищ установлены внутри тестового образа.

Артефакты каждого запуска находятся в `build/lab2/runs/<run-id>/`:

- `allure-report/index.html` — автономный HTML-отчёт;
- `unit.jsonl`, `integration.jsonl`, `e2e.jsonl` — вывод Go;
- `pipeline.json`, `baseline.json`, `cleanup.json` — этапы и состояние хранилищ;
- `curl-replay.log`, `traffic.pcap`, `traffic.txt` — повтор E2E через curl и захваченный HTTP-трафик;
- `api.log`, `setup.log`, `runner.log`, `compose.log`, `teardown.log` — диагностика приложения и стенда.

Для повторного использования заведомо актуального образа:

```sh
make lab2-build
LAB2_TEST_IMAGE=watchtower-lab2-tests:local LAB2_SKIP_BUILD=1 make lab2
```

После изменения исходников образ нужно пересобрать. Обычный `make lab2` делает это автоматически. При необходимости задайте уникальное имя запуска через `LAB2_RUN_ID`: строчные латинские буквы, цифры и дефис.

## Стенд и сценарии

В отдельной сети Compose работают PostgreSQL 18 с pg_partman и pg_cron, Redis, HTTP-сервис `probe` и контейнер тестов. В последнем запускается настоящий `cmd/api` с фоновыми компонентами приложения. Контролируемый адрес `http://probe:8081/health` отвечает HTTP 200 и не зависит от доступности внешних сайтов. Порты на хост не публикуются.

Интеграционные сценарии находятся в [tests/lab2/integration](../../tests/lab2/integration): авторизация, контакты, окна обслуживания, владение ресурсами, жизненный цикл общей цели, результаты проверок и кэш метрик. Используются настоящие репозитории и сервисы; PostgreSQL-моки ЛР №1 здесь не применяются. Каждый сценарий расположен в отдельном файле и один раз создаёт исходные данные, затем выполняет последовательность действий с проверками.

[HTTP E2E](../../tests/lab2/e2e/monitor_http_test.go) регистрирует пользователя, получает JWT, проверяет защиту API, создаёт монитор, дожидается фоновой проверки с результатом `up`/HTTP 200, читает метрики, редактирует, отключает, включает и удаляет монитор. [replay.py](../../tools/lab2/replay.py) повторяет этот путь командами curl. tcpdump сохраняет трафик обоих сценариев. В записи присутствуют только учётные данные одноразовых тестовых пользователей.

## Восстановление и изоляция

Миграции создают настоящую схему. Перед сценариями и после них очищаются прикладные таблицы, в сценарии кэша — также Redis. Завершающая секция конвейера останавливает API, повторяет очистку всех таблиц и Redis и проверяет нулевые счётчики. Результат записывается в `cleanup.json`. Затем Compose удаляет контейнеры, сеть и временное хранилище PostgreSQL.

Каждый запуск получает отдельное имя Compose-проекта, сеть, PostgreSQL и Redis. Это позволяет запускать тесты одновременно без общих данных и конфликтов портов. Общая история Allure обновляется под файловой блокировкой.

Шина приложения — непостоянный GoChannel внутри процесса. Интеграционные подписчики читают сообщения и вызывают `Ack`, после сценария шина закрывается. Остановка API уничтожает его очередь в памяти. Серверного хранилища пользовательских сессий нет: авторизация использует JWT. API получает новый случайный ключ для каждого запуска; при завершении процесс и файл с ключом удаляются.

Для проверки повторяемости и отказов:

```sh
LAB2_INTEGRATION_REPEAT=2 make lab2
LAB2_FAIL_STAGE=integration make lab2
LAB2_FAIL_STAGE=e2e make lab2
```

Последние две команды намеренно завершаются с ошибкой после соответствующего этапа. Перед ошибкой в хранилища записываются контрольные данные, которые завершающая очистка должна удалить. Следующий этап отмечается `skipped` в Allure, отчёт формируется и при ошибке. Обработка SIGINT/SIGTERM даёт время на очистку; при принудительном уничтожении процесса восстановление обеспечивается удалением одноразового стенда, а формирование отчёта требует работающего процесса.

При ошибке сборки или готовности стенда скрипт сохраняет причину и результаты `setup: failed`, остальные этапы — `skipped`. Для HTML используется уже собранный образ или установленный локально Allure. Если ни того ни другого нет, сохраняются исходные результаты и явное сообщение о невозможности сформировать HTML. Сам скрипт проверяется без Docker командой `python3 -m unittest tools/lab2/test_run.py`.

## CI и история Allure

[GitHub Actions](../../.github/workflows/tiopo-lab2.yml) выполняет checkout и `make lab2` для push в `TIOPO-2`, pull request или ручного запуска. История `build/lab2/history/history.jsonl` восстанавливается из кэша и сохраняется после тестов; загрузка отчётов и логов выполняется с `if: always()`. Данные между локальными запусками сохраняются в том же каталоге истории. Настройка соответствует [механизму истории Allure 3](https://allurereport.org/docs/history-and-retries/).

Фактические проверки и ограничения приведены в [results.md](results.md). Краткое соответствие требованиям — в [requirements.md](requirements.md).
