# ЛР №5 — BDD-аутентификация

WatchTower проверяется через настоящий HTTP API, PostgreSQL, Redis и SMTP. Behave выполняет Gherkin-сценарии, Mailpit принимает письма, Allure показывает шаги и результат каждого сценария. Ветка `TIOPO-5` основана на `TIOPO-4`.

## Запуск

Нужны Docker Engine с Compose и Python 3.10+. Для первоначальной сборки нужен доступ к реестрам образов, Go modules, npm и PyPI.

```sh
make lab5-check
make lab5
```

При использовании отдельной Colima VM:

```sh
colima start watchtower-lab2 --activate=false --ssh-config=false
DOCKER_CONTEXT=colima-watchtower-lab2 make lab5
```

Результаты находятся в `build/lab5/runs/<run-id>`, путь последнего запуска — в `build/lab5/latest.txt`. Открыть Allure:

```sh
python3 -m http.server 8088 --directory "$(cat build/lab5/latest.txt)/allure-report"
```

Адрес: <http://localhost:8088>. `manifest.json` содержит коды завершения этапов. `domain-tests.jsonl` — безопасные имена и статусы проверок MFA на PostgreSQL. Пароли, OTP, recovery-токены и содержимое писем в отчёт не прикладываются.

## Поведение приложения

Режим включается параметром `auth.mfa.enabled: true` в конфигурации настоящего API. В этом режиме используется PostgreSQL, а прежние `/auth/login` и `/auth/register` отвергают запросы: получить JWT по одному паролю нельзя. При выключенном режиме сохраняется поведение предыдущих лабораторных. Новые маршруты описаны в [OpenAPI](../../api/mfa.openapi.yaml); запущенный API отдаёт спецификацию по `/openapi-mfa.yaml` и показывает её в `/swagger`.

1. Регистрация сохраняет bcrypt-хэш пароля и email.
2. Верный пароль создаёт challenge и отправляет шестизначный email-код на пять минут. Ответ не содержит JWT.
3. Верный одноразовый код завершает MFA. После трёх неудачных вводов пароля или кода учётная запись блокируется; успешный первый фактор сам по себе не обнуляет счётчик.
4. Восстановление отправляет на зарегистрированный email случайный одноразовый токен на десять минут. Его подтверждение с новым паролем снимает блокировку и отзывает прежние сессии и коды. Запрос восстановления неизвестного пользователя возвращает тот же ответ.
5. Через 90 дней требуется смена пароля. Даже после MFA выдаётся ограниченный JWT: он разрешает только смену пароля с подтверждением текущего. Запросы к мониторам отвергаются. Уже выданные JWT также перестают давать доступ при истечении срока пароля.
6. Обычная смена пароля и восстановление увеличивают версию сессий. Все старые JWT, OTP и recovery-токены становятся недействительными; нужен новый вход с MFA.

Политика паролей: 1–72 байта UTF-8, новый пароль должен отличаться от текущего. Проверки лимита и одноразовости используют блокировку строки в транзакции; параллельные запросы не могут дважды принять один код или потерять увеличение счётчика. JWT проверяется по HS256, issuer, сроку, MFA-признаку, scope и текущему состоянию учётной записи.

SMTP по умолчанию требует STARTTLS с проверкой сертификата. Только для изолированного Mailpit стенд задаёт `allow_insecure_smtp: true`. Контейнеры не публикуют порты на хост. Внешняя почтовая доставка и интерфейс браузера в этой работе не тестируются: E2E проходит через HTTP и настоящий локальный SMTP.

## BDD и изоляция

[authentication.feature](../../tests/lab5/features/authentication.feature) описывает успешный вход, неверные данные, блокировку, восстановление, истечение и повторное использование секретов, плановую и обычную смену пароля, отзыв JWT, параллельные попытки и изоляцию пользователей.

Перед каждым сценарием генерируются уникальные login/email и случайный пароль. Учётная запись создаётся HTTP-запросом. Cleanup удаляет пользователя из одноразовой БД и проверяет каскадное удаление состояния MFA; он выполняется и после ошибки сценария. После всего прогона удаляются контейнеры, сеть и том БД.

Для проверки истечения сроков сценарий сдвигает timestamp в тестовой БД. Это подготовка состояния для E2E, а не тестовый маршрут в приложении: все действия аутентификации и проверки доступа затем выполняются через HTTP. Ждать 90 дней не требуется.

Пароли пользователей и ключи подписи генерируются во время запуска. Пароль БД и конфигурация API находятся во временном каталоге `build/lab5/private` с правами 0700 и файлами 0600, за пределами публикуемых артефактов; после прогона каталог удаляется. В GitHub Secrets не требуется заранее создавать техническую учётную запись: она одноразовая и не существует до теста. Mailpit с письмами также удаляется. В сохранённых результатах остаются только безопасные статусы и формулировки BDD-шагов.

## CI и диагностика

[Workflow](../../.github/workflows/tiopo-lab5.yml) выполняет проверки runner, реальную PostgreSQL-регрессию и BDD. Ошибка доменных тестов не мешает выполнению BDD; итоговый код остаётся неуспешным. Allure создаётся после тестовых ошибок, артефакты загружаются через `always()`. Если сам генератор недоступен, сохраняются исходные результаты и явно обозначенная HTML-сводка инфраструктурной ошибки; она не выдаётся за Allure.

Логи сборки доступны в `build-app.log` и `build-postgres.log`. Вывод рабочих процессов фильтруется, чтобы исключить утечки credentials. При долгой команде runner печатает сообщение о продолжении работы. Диагностика сценария находится в шагах Allure; HTTP-ошибки показывают метод, маршрут и код без тела ответа и секретов.

Таблица требований: [requirements.md](requirements.md). Фактический результат прогона: [results.md](results.md).

## Двухфакторный вход в UI

Интерфейс поддерживает вход с email-кодом, регистрацию с email, восстановление заблокированного аккаунта и обязательную смену истёкшего пароля. Режим выбирается переменной UI `REACT_APP_AUTH_MFA=true`; backend должен работать с `auth.mfa.enabled: true`. JWT сохраняется только после второго фактора. Ограниченный токен смены пароля хранится в памяти до завершения формы; обновление страницы требует повторного входа.

Для локального стенда используется `docker-compose.mfa.yaml` вместе с основным Compose и локальными настройками портов. Конфигурация `build/run/mfa-config.json` — копия `docker/config.yaml` с добавленным `auth.mfa`: `enabled: true`, `smtp_address: mailpit:1025`, `smtp_from: watchtower@example.test`, `allow_insecure_smtp: true`. Файл содержит локальные credentials: его нужно создавать с правами 0600, он исключён из Git. Для обычной SMTP-доставки нужен сервер с STARTTLS.

На подготовленном локальном стенде:

```sh
DOCKER_CONTEXT=colima-salt-operator-e2e docker compose -p watchtower \
  -f docker-compose.yaml -f build/run/compose.override.yaml -f docker-compose.mfa.yaml up -d --build
```

Интерфейс: <http://localhost:3000>, API: <http://localhost:8081>, почтовый ящик Mailpit: <http://localhost:8025>. Mailpit принимает письма локально, внешняя отправка не выполняется. Старые аккаунты без email и записи `auth_mfa` автоматически не переводятся: для проверки зарегистрируйте новый аккаунт.

Проверка UI: `CI=true npm test --prefix watchtower-ui -- --watchAll=false --runInBand`; production-сборка: `REACT_APP_AUTH_MFA=true npm run build --prefix watchtower-ui`.
