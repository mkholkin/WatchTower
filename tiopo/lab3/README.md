# ЛР №3 — микробенчмаркинг JSON

Сравниваются `encoding/json` из Go 1.26.3 и `github.com/goccy/go-json` 0.10.6. Вторая библиотека уже была зависимостью проекта; приложение продолжает использовать прежнюю реализацию. Измеряется обработка настоящего типа ответа API `gen.MonitorCheck`, включая UUID, время, необязательные поля, Unicode и экранируемые символы.

## Запуск

Нужны Docker с Linux-контейнерами, Python 3.10+ и Make. Go нужен только для отдельной команды проверки исходников.

```sh
make lab3-check
make lab3
```

`make lab3` выполняет 100 независимых испытаний. На каждом испытании проверяются обе библиотеки, три сценария и два размера массива — всего 1200 результатов. Docker-образ содержит закреплённые версии Go, go-json, Matplotlib и Allure; после сборки сеть при измерениях отключена. Ход испытаний виден в терминале и GitHub Actions.

```sh
make lab3-smoke
```

Это один диагностический прогон полного пути. Он не засчитывается как выполнение требования о 100 испытаниях: в Allure такие измерения отмечены `skipped`.

На этой машине используется отдельный профиль Colima. Существующие профили не перезапускаются, глобальный контекст не меняется:

```sh
colima start watchtower-lab3 --vm-type vz --cpu 1 --memory 2 --disk 15 --activate=false --ssh-config=false --mount "$PWD:w"
DOCKER_CONTEXT=colima-watchtower-lab3 make lab3
```

Если Docker недоступен, можно проверить сборку, расчёт статистики и отчёт на хосте. Для этого нужны Go, Node, установленные зависимости `tools/lab1` и Python-окружение с `tools/lab3/requirements.txt`:

```sh
python3 -m venv .cache/lab3-venv
.cache/lab3-venv/bin/pip install -r tools/lab3/requirements.txt
.cache/lab3-venv/bin/python tools/lab3/run.py --native --smoke --trials 1
```

Нативный режим всегда диагностический: он не доказывает Docker-изоляцию и не получает статус `passed` в Allure.

## Сценарии и единица измерения

- `encode`: сериализация массива из 1 или 32 результатов проверки.
- `decode`: десериализация заранее подготовленного JSON в новый массив.
- `roundtrip`: сериализация и последующая десериализация одного массива.

Одна операция — весь указанный сценарий над массивом, а не один элемент массива. Для `roundtrip` это два преобразования. Перед таймерами проверяются совпадение JSON и восстановление исходных структур. Данные детерминированы; порядок 12 комбинаций перемешивается с seed, равным номеру испытания. Результаты сохраняются в переменных, используемых программой, чтобы компилятор не удалил полезную работу.

Каждый сценарий выполняет 256 операций warmup, 16 пакетов по 64 операции основного измерения, 256 отдельно измеряемых операций для перцентилей запросов и 64 операции teardown/cooldown. Всего — 1600 операций на сценарий и 1 920 000 полезных операций за полный запуск. Подготовка данных, проверки эквивалентности и контрольные вызовы инструмента в это число не входят. После teardown ссылки на данные освобождаются; завершение контейнера удаляет остальное состояние.

Принудительная сборка мусора выполняется перед warmup каждого сценария. Во время измерений автоматическая GC включена: `GOGC=100`, `GOMEMLIMIT=384MiB`. JSON-операции включают обычные для них выделения памяти.

## Равные условия

Для запуска собирается общий базовый образ. Для каждого испытания создаётся отдельный образ, отличающийся только меткой номера испытания: все слои с бинарным файлом, библиотеками и настройками одинаковы. Новые контейнеры запускаются последовательно, с `GOMAXPROCS=1`, привязкой к CPU 0, лимитом 1 CPU, памятью 512 MiB, без swap сверх этого лимита и без сети. Корневая файловая система доступна только для чтения.

`manifest.json` сохраняет реальные идентификаторы образов и контейнеров, `HostConfig` и окружение из `docker inspect`. Перед созданием отчёта проверяются уникальность образов/контейнеров и совпадение конфигурации. Контейнер и образ испытания удаляются после снятия данных; базовый образ — после построения отчёта. Неудачные запуски оставляют диагностику, завершаются с ошибкой и не выдаются за полную серию.

Лимит CPU и affinity внутри VM не исключают конкуренцию с процессами хоста. VM, ОС, архитектура и версия Go фиксируются в артефактах; результаты разных машин нельзя объединять в одно распределение. Для сравнения библиотек используются парные измерения внутри каждого испытания.

## Время, overhead и статистика

Основная величина `ns/op` — время пакета, делённое на 64 операции. Вызовы часов находятся за пределами внутреннего цикла. Инструмент отдельно измеряет миллион вызовов контрольной операции через тот же цикл и проверку ошибки после 10 000 прогревочных вызовов. Контрольная операция не инлайнится и изменяет счётчик. Её стоимость входит в оценку overhead; измеренная оценка не вычитается из результата. К оценке цикла добавляется стоимость пары чтений часов, делённая на размер пакета: `amortized_overhead_ns_per_op`. Превышение желательных 5 нс этой общей оценкой выводится как предупреждение, а не скрывается.

Перцентили **отдельных запросов** вычисляются по 256 одиночным измерениям на испытание, то есть по 25 600 значениям для каждой комбинации. Они включают инструментальную стоимость чтения часов. Полная стоимость пары чтений часов оценивается отдельным пакетом из 100 000 вызовов (`timer_pair_ns_per_op`). Дополнительно сохраняются 256 коротких контрольных интервалов (`timer_probe_ns`); на виртуальном таймере часть интервалов может округляться до нуля, что не означает бесплатное измерение. Эти значения нельзя смешивать с распределением средних по пакетам или трактовать как сетевую задержку.

Используется nearest-rank: для перцентиля `p` выбирается элемент с номером `ceil(p × N)` в отсортированном массиве. Выводятся p50, p75, p90, p95 и p99, среднее, минимум и максимум. Warmup и teardown исключены из обоих распределений, но их число операций и время сохраняются. Полное время каждого сценария и испытания включает подготовку; `campaign_seconds` дополнительно включает Docker-сборку и запуск контейнеров до формирования отчёта.

## Артефакты и CI

Результаты находятся в `build/lab3/runs/<run-id>/`:

- `raw/trial-*.json` — исходные результаты всех фаз, пакетов и отдельных операций.
- `manifest.json` — конфигурация, идентификаторы, длительность кампании и ошибки.
- `summary.json`, `summary.csv` — агрегаты и перцентили; `samples.csv` — отдельные наблюдения.
- `plots/*.svg`, `plots/*.png` — временной ряд, ECDF по числу запросов и гистограмма; хвост распределения не отбрасывается.
- `results.md` — таблица результатов, парные отношения времени и предупреждения.
- `allure-results/`, `allure-report/` — Allure с графиками и статистикой каждой комбинации.
- `setup.log`, `report.log`, `allure.log`, `raw/*.stderr` — диагностика.

Workflow `tiopo-lab3.yml` запускает проверки корректности и 100 испытаний, затем загружает артефакты даже при ошибке. Измерения на общедоступном CI runner отражают конкретный запуск и не являются строгим performance gate.

Краткое соответствие заданию — [requirements.md](requirements.md), фактические результаты — [results.md](results.md). Методические источники: [таймеры и подготовка Go-бенчмарков](https://go.dev/blog/testing-b-loop), [API go-json 0.10.6](https://github.com/goccy/go-json/tree/v0.10.6). Используется собственный минимальный цикл измерения, разрешённый заданием, чтобы явно учитывать фазы и собирать отдельные задержки.
