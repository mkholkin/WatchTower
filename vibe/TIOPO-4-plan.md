# ЛР №4: нагрузочное тестирование WatchTower

Ветка `TIOPO-4` наследует `TIOPO-3`. Выполнить требования `tiopo/ТИОПО, ЛР №4.pdf` на реальном HTTP API, PostgreSQL и Redis. Измерения запросов, а не микробенчмарки; генератор k6 1.3.0.

1. Создать `tests/lab4/model.mjs`, `model.test.mjs`, `journey.js`: вход, создание монитора, просмотр списка/деталей/проверок/SLA, изменение, удаление и пауза. Профили ramp, stress/recovery, soak с 0/10/20% ошибочных операций; warmup выделен отдельно. Проверить `node --test tests/lab4/model.test.mjs` и Docker smoke.
2. Создать `tools/lab4/compose.yaml`, Dockerfile, `run.py`, `collect.py`: свежие образы API на сценарий, отдельные БД/тома/сети, одинаковые лимиты, CPU 0 для API, CPU 1 для хранилищ, CPU 2 для k6, CPU 3 для мониторинга. Сохранить Docker inspect и CPU/RAM/дисковые счётчики каждые 1 с. Проверить преобразование метрик и обязательную очистку.
3. Создать `tools/lab4/report.py`, `test_report.py`, Allure config: временные ряды, ECDF, гистограммы, p50/p75/p90/p95/p99; распределения RPS по 5-секундным окнам, ресурсы min/max/median, границы SLO и время восстановления. Проверить расчёты на известных данных.
4. Добавить `make lab4`, `lab4-smoke`, `lab4-check`, GitHub Actions, README и краткую таблицу требований. Выполнить пять полных сценариев, сохранить фактические результаты и графики, подтвердить очистку, создать коммит.

SLO для анализа: p95 полного времени запроса ≤ 500 мс, неожиданные ответы/таймауты ≤ 1%. Восстановление: три последовательных 5-секундных окна после перегруза с выполненным SLO и успешным RPS ≥ 80% медианы baseline. Отсутствие отказа/восстановления в пределах испытания отражается явно, данные не подгоняются. Минимальный объём полного сценария — 1000 запросов; soak — 300 секунд после warmup. Closed-model throughput относится к выбранному сценарию с паузами, не к максимальному RPS произвольного endpoint.

Источники: https://grafana.com/docs/k6/latest/using-k6/scenarios/ ; https://docs.docker.com/reference/api/engine/version/v1.51/ .
