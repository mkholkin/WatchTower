# ЛР №5: BDD-проверка аутентификации

**Цель:** выполнить `tiopo/ТИОПО, ЛР №5.pdf`: E2E с вторым фактором, лимитом попыток, восстановлением и плановой сменой пароля. Ветка `TIOPO-5` от `TIOPO-4`.

**Решение:** включаемый режим MFA в настоящем API WatchTower, PostgreSQL для атомарного состояния и хэшей, SMTP для доставки одноразовых секретов. BDD на Behave/Gherkin через HTTP; локальный Mailpit принимает настоящие SMTP-письма. Allure сохраняется при ошибках. Сценарии создают случайные учётные записи и удаляют их; секреты генерируются в памяти и не выводятся в отчёт.

## Контракт

Все новые маршруты имеют префикс `/auth/mfa`:

| POST | JSON | Ответ |
|---|---|---|
| `/register` | login, email, password | 201 |
| `/login` | login, password | 202: challenge_id; JWT отсутствует |
| `/verify` | challenge_id, code | 200: access_token, password_change_required |
| `/recover` | login | 202, одинаково для неизвестного пользователя |
| `/reset` | login, token, new_password | 204 |
| `/password` | current_password, new_password; Bearer token | 204 |

Ошибки: 400 — формат/политика пароля; 401 — неверные credentials/код/токен; 423 — блокировка; 410 — истёкший код/токен; 409 — существующая запись; 503 — доставка недоступна. Защищённый `GET /monitors` проверяет доступ. Старые `/auth/login` и `/auth/register` не обходят MFA в новом режиме. JWT после истечения срока пароля разрешает только смену пароля. Смена/сброс пароля отзывает прежние JWT и challenges.

Политика: минимум 12 и максимум 72 байта пароля, 3 неудачные попытки, код из 6 цифр на 5 минут, токен восстановления на 10 минут, срок пароля 90 дней. Секреты случайные, хранятся только хэши. Истечение срока в E2E задаётся обновлением timestamp в одноразовой БД, без ожидания 90 дней и без тестовых HTTP-backdoor.

## Этапы

1. `internal/service/mfa/`, миграция: регистрация, login challenge, одноразовая проверка, блокировка, восстановление, смена и отзыв токенов. Транзакционные блокировки защищают счётчики и одноразовость. Проверка: `go test ./internal/service/mfa` и E2E на PostgreSQL.
2. `configs/`, `internal/app/app.go`, `cmd/api/main.go`, HTTP-обработчик и SMTP: подключить новый режим, запретить обход через старый вход; описать API. Проверка: сборка API, тесты HTTP/SMTP и прежней auth-службы.
3. `tests/lab5/`: Gherkin/Behave для успешного MFA, неверных данных, лимитов пароля/OTP, восстановления, срока/повторного использования OTP и reset token, плановой и обычной смены пароля, отзыва JWT и изоляции пользователей. Проверка: полный реальный E2E-прогон, Allure без секретов.
4. `tools/lab5/`, Makefile, GitHub Actions: изолированный Docker-стенд, случайные технические секреты, cleanup в finally, отчёт даже после ошибки. `tiopo/lab5/`: методика, результаты и таблица требований. Проверка: `make lab5`, `make lab5-check`, независимое ревью, коммит.

## Проверка рисков

- Нельзя получить access JWT только по паролю или через прежний маршрут.
- Параллельные попытки не обходят лимит; OTP/reset token нельзя использовать дважды.
- После блокировки/смены пароля старый JWT не авторизует запросы.
- Истёкший пароль не даёт доступ к мониторам до смены.
- Артефакты/исключения/BDD-шаги не содержат паролей, кодов и токенов; пользователи удаляются и после ошибки сценария.
