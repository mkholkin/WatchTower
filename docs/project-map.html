02

От настройки до уведомления

  1. Найти общую цель и создать мониторMonitoring Management вычисляет хеш endpoint + протокол + сетевая конфигурация. Пользователь и ожидания в хеш не входят. Сервис
  2. Назначить сетевую проверкуScheduler загружает активные Target из БД и обновляет расписание по событиям. Примерно раз в секунду отправляет подошедшие цели работникам. Планировщик
  3. Получить сырой ProbeResultWorkerPool вызывает HTTP-prober и сохраняет время, задержку, код ответа и сетевую ошибку в БД. UP/DOWN на этом шаге не определяется. Работник
  4. Оценить результат для каждого подходящего монитораAnalyzer читает БД каждые 500 мс, применяет ожидания и приоритет maintenance, формирует сводки и обновляет состояние. Анализатор
  5. Доставить смену статуса и показать историюСобытие monitor.status_changed поступает в Notification. Активные контакты получают Telegram-сообщение; UI читает сводки и SLA через Metrics API. Уведомления
Порядок операций имеет значение. Analyzer публикует событие во время оценки, до записей в commit. Записи и публикация не объединены одной транзакцией. Очередь уведомлений при переполнении отбрасывает задачи.
03

Target ≠ Monitor

Target / общая цель

Endpoint, сетевой протокол и конфигурация, активность и интервал проверки.

domain/entity/target

Monitor / взгляд пользователя

Владелец, ссылка на Target, ожидания к ответу, интервал, статус, контакты и обслуживание.

domain/entity/monitor
User1 → NMonitor / AlertContact / MaintenanceWindow
Target1 → NMonitor / ProbeResult
Monitor1 → NMonitorStatusLog
MonitorN ↔ NAlertContact / MaintenanceWindow

Как получается сводка

В PostgreSQL: probe_result + monitor + monitor_status_log через SQL JOIN. Отдельной таблицы ProbeSummary нет; методы записи сводок — no-op. MongoDB сохраняет отдельные документы.

SQL сводок

Как считается SLA

UP / (UP + DOWN) × 100

По длительности интервалов истории. MAINTENANCE и UNKNOWN не входят в знаменатель.

SQL метрик · Триггер истории

Сырые проверки партиционируются по времени: часовые партиции pg_partman, обслуживание через pg_cron. Миграция.

Запуск и инструменты

Команды запуска взяты из конфигурации проекта. Отдельно проверены компиляция API и unit-тесты без PostgreSQL/Testcontainers.

# Полный стек: UI 3000 / API 8080 / PostgreSQL 5432 / Redis 6379
docker compose up --build

# API локально, с готовой инфраструктурой из YAML

# Make собирает CLI
make build
./build/watchtower configs/config.yaml

make gen-repo → sqlc
make mocks → mockgen

Генерируемые каталоги: api/http/v1/gen, postgres/sqlcgen, service/testmocks.

Команда завершилась успешно 20.09.2026.

Весь модуль не собирается

go build ./... ломается на cmd/cli: CLI использует старые сигнатуры четырёх сервисных API.

Dockerfile.backend собирает только рабочий cmd/api, а make build — проблемный cmd/cli.

Тесты частично устарели

Прошли analyze, auth и common/provider. Healthcheck и monitoring_management не компилируют тесты; contacts и maintenance падают.

PostgreSQL-интеграция не запускалась. TypeScript не проверен: node_modules отсутствует.
07

Что важно не перепутать

Реализованы HTTP и Telegram

TCP/ICMP-prober содержат panic("implement me"); в App зарегистрирован только HTTP. Методы Validate() у ожиданий всех протоколов и у ICMP-конфигурации также не реализованы. Email/SMTP упомянуты в README/C4, но подключённого провайдера нет. TCP · Expectations · Регистрация.

API работает как отдельная сборочная цель, CLI отстал

cmd/api компилируется. cmd/cli вызывает удалённые или изменённые GetSummaries, ParseToken, CreateMonitor и поле TotalDowntime, поэтому go build ./... и текущий make build завершаются ошибкой.

Maintenance не означает полное отключение сообщений

Анализатор присваивает MAINTENANCE, SLA исключает этот интервал. Notification не фильтрует переходы в/из maintenance и уведомляет активные контакты при событии смены статуса. Обработка события.

Связи требуют аудита владения

Добавление и удаление связи Monitor ↔ MaintenanceWindow не сравнивает владельцев объектов с текущим пользователем. Связь Monitor ↔ AlertContact проверяет владельца монитора, но не контакта.

Есть ошибки в распространении ошибок

service.Error.Error() объединяет пустой список, getOrCreateTarget проглатывает часть ошибок репозитория, а EnableMonitor — ошибку синхронизации Target. Это может скрывать первопричины и искажать HTTP-ответ.

Переменная API URL в Compose не совпадает с Axios

Compose задаёт REACT_APP_API_BASE_URL, клиент читает REACT_APP_API_URL. Локальный fallback http://localhost:8080 совпадает с портом API, но заданная переменная клиентом не используется.

MongoDB не заменяет PostgreSQL при запуске целиком

Репозитории выбираются по сервисам, но InitApp безусловно вызывает PostgreSQL-миграции. MongoDB-сервиса в Compose нет. CLI собирает PostgreSQL-репозитории напрямую.

Миграции и схема sqlc расходятся

Миграции делают probe_result партиционированной таблицей с составным ключом и добавляют ограничения уникальности. Отдельная postgres/schema/schema.sql для sqlc описывает обычный UUID primary key и не содержит этих ограничений.

Лабораторные отчёты не подтверждают текущие тесты

В документации есть make lab1, test-unit, test-integration и ссылки на отсутствующие скрипты. Свежий ограниченный прогон нашёл несовместимые моки и тесты. Benchmark-цели Makefile также ссылаются на отсутствующий каталог benchmarks.

Часть параметров фоновых служб зашита в код

App: PostgreSQL — 200 работников и очередь 10 000; MongoDB — 5 и 100. Переданные анализатору значения −1 заменяются конструктором на лимиты 1000/500, а не отключают ограничения.
