# WebLab № 2 — отчёт о выполнении

Ветка: WEB-2.
Назначение: проектирование публичного REST API WatchTower без реализации серверных обработчиков.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Версия API | Новый контракт публикуется как /api/v2/…, поскольку в проекте уже есть работающий API. Совместимость старой реализации рассматривается в WebLab № 3. |
| Формат | OpenAPI 3.1.0 в YAML; источник истины — api/openapi.yaml. |
| Стиль | Ресурсы адресуются существительными. Включение и отключение выполняются через PATCH поля is_enabled, а связи — через идемпотентные PUT/DELETE подресурсы. |
| Авторизация | Регистрация и получение токена публичны; остальные операции используют Bearer JWT и описывают ответы 401/403. |
| Нереляционный транспорт | Внешним клиентам достаточно REST. Внутренние проверки и события не требуют отдельного публичного SSE, WebSocket, gRPC или брокерного контракта. |
| Проверка без backend | make validate-api загружает контракт, проверяет ссылки и схемы, применяет REST-правила и валидирует встроенные примеры запросов и ответов. |

## Состав API

| Семейство | Возможности |
|---|---|
| Пользователи и токены | Регистрация пользователя, получение JWT |
| Мониторы | Полный CRUD, частичное обновление, включение и отключение через PATCH |
| Метрики | Проверки, интервалы статусов, SLA |
| Контакты | Полный CRUD Telegram-контактов, включение и отключение через PATCH |
| Окна обслуживания | Полный CRUD разовых и ручных окон |
| Связи | PUT/DELETE для контакта монитора и монитора окна обслуживания |

Итоговый контракт содержит 13 путей, 24 операции с уникальными operationId, три операции PATCH и 24 именованных примера.

## Соответствие требованиям

| № | Требование лабораторной | Где подтверждено |
|---:|---|---|
| 1 | OpenAPI 3.1+ и пути вида /api/v<версия>/… | [api/openapi.yaml](../../api/openapi.yaml): OpenAPI 3.1.0, все пути начинаются с /api/v2/ |
| 2 | Основной результат — YAML-описание API | [api/openapi.yaml](../../api/openapi.yaml) |
| 3 | Решение по взаимодействиям вне REST | Раздел «Принятые решения» в этом файле; отдельный публичный транспорт не требуется |
| 4 | Полный CRUD хотя бы одной сущности | [операции Monitor](../../api/openapi.yaml): GET/POST коллекции и GET/PATCH/DELETE ресурса |
| 5 | Частичный UPDATE | PATCH /api/v2/monitors/{monitorId} со схемой MonitorPatch; также PATCH контактов и окон |
| 6 | Достаточный набор ресурсов и методов | 24 операции для аутентификации, мониторов, метрик, контактов, окон и связей в [контракте](../../api/openapi.yaml) |
| 7 | Корректные методы, статусы, заголовки и идемпотентность | Операции, BearerAuth, Location и WWW-Authenticate в [api/openapi.yaml](../../api/openapi.yaml); PUT/DELETE связей идемпотентны |
| 8 | Автоматический линтер и проверка примеров по схемам без backend | [api/openapi_test.go](../../api/openapi_test.go), цель validate-api в [Makefile](../../Makefile) |

## Проверка

~~~bash
make validate-api
~~~

Проверка подтверждает:

- структурную корректность и разрешение всех ссылок;
- OpenAPI 3.1.0 и префикс /api/v2/;
- уникальность и наличие operationId;
- отсутствие RPC-путей /enable и /disable, завершающих / и тел у DELETE;
- полный CRUD Monitor и отдельную схему частичного обновления;
- соответствие встроенных примеров схемам.

Сгенерированный сервер и текущие обработчики намеренно не менялись: их реализация относится к WebLab № 3.

## Результаты проверки

| Команда | Результат |
