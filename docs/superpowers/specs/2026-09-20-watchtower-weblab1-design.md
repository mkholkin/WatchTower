# Спецификация выполнения WebLab № 1 для WatchTower

## Цель

Подготовить комплект материалов базового трека WebLab № 1 для существующего проекта WatchTower. Комплект должен покрывать все 11 пунктов задания, соответствовать фактическому состоянию проекта и максимально переиспользовать существующие документы, диаграммы и изображения.

Требования ИИ-трека в работу не входят. Файлы `AGENTS.md`, `AI_CONTEXT.md` и `AI_REVIEW.md` не создаются.

## Источники истины

При расхождениях материалы проверяются в следующем порядке:

1. исходный код и composition root приложения;
2. `api/openapi.yaml` для HTTP-контракта;
3. миграции для фактической схемы PostgreSQL;
4. существующие документы и диаграммы.

Нереализованные возможности отделяются от работающих. SMTP, WebSocket, TCP- и ICMP-проверки нельзя описывать как готовые функции текущей версии.

## Основной отчёт

Основным документом лабораторной станет существующий `README.md`. Это соответствует последующей WebLab № 4, где содержимое первой работы должно быть доступно по маршруту `/documentation`.

В `README.md` должны появиться:

1. цель системы и решаемая проблема;
2. краткий перечень функциональных требований;
3. измеримые нефункциональные требования к производительности, надёжности и безопасности;
4. ссылки на Use Case и три нелинейные BPMN-диаграммы;
5. не менее трёх пользовательских сценариев с предусловиями, основным и альтернативными потоками;
6. ссылки на ER-диаграмму и диаграмму базы данных;
7. фактический технологический стек;
8. ссылки на C4 Context, Container и Component;
9. существующие эскизы Dashboard и страницы монитора;
10. два кратких ADR с решением, альтернативами и причинами выбора;
11. команды запуска и навигация по исходникам диаграмм.

## Новый материал

Добавляется третья нелинейная BPMN-диаграмма управления окном обслуживания. Процесс включает выбор типа окна, проверку интервала или ручного состояния, привязку мониторов, обработку ошибочных данных и влияние активного окна на результат анализа.

Добавляется `docs/labs/WEB-1.md` — короткая запись о выполненной работе: состав результата, переиспользованные материалы, существенные уточнения и выполненные проверки.

## Архитектурные решения

В основной отчёт включаются два кратких ADR.

### ADR-001. Модульный монолит

Выбран единый Go-процесс с внутренними модулями API, управления мониторами, планирования, анализа и уведомлений. Альтернативы: набор микросервисов и монолит без модульных границ. Решение уменьшает эксплуатационную сложность учебного проекта, сохраняя явные интерфейсы и возможность будущего выделения сервисов.

### ADR-002. PostgreSQL и Redis

PostgreSQL выбран основным хранилищем конфигурации, результатов проверок и истории статусов. Redis используется только как необязательный кэш последних сводок. Альтернативы: хранение всего в PostgreSQL без кэша и MongoDB как основное хранилище. Решение сохраняет транзакционную модель данных и ускоряет чтение горячих данных без превращения кэша в источник истины.

## Проверка результата

Готовый комплект проверяется так:

1. чек-лист из 11 пунктов основного задания сопоставляется с разделами `README.md`;
2. все относительные ссылки и пути к локальным файлам проверяются автоматически;
3. изменённые PlantUML-диаграммы проверяются доступным локальным рендерером или синтаксической проверкой;
4. выполняется просмотр Git diff, чтобы исключить изменения кода и пользовательских артефактов;
5. при доступности текущего Go-окружения повторяется минимальная сборка API `go build -o /tmp/watchtower-api-check ./cmd/api`.

## Границы работы

WebLab № 1 не изменяет бизнес-логику, API, схему данных, конфигурацию развёртывания или UI. Исправление известных дефектов приложения, реализация TCP/ICMP/SMTP и требования WebLab № 2–9 остаются за пределами этой ветки.
